## Аналіз README: що насправді вимагається

| Вимога | Що за нею стоїть технічно |
|---|---|
| Черга URL, ліміт одночасних завантажень | Пул з N робочих потоків, спільна черга під mutex, `condition_variable_any` для «є робота» |
| Прогрес і швидкість для кожного файлу | Лічильники, які пише робочий потік, а читає UI → `std::atomic` або знімок під mutex; швидкість — за вікном часу (`steady_clock`) |
| Пауза / продовження / скасування | Перервати передачу **зсередини** libcurl: progress-callback повертає ненуль → `CURLE_ABORTED_BY_CALLBACK`. Пауза зберігає `.part`, скасування — видаляє |
| Збереження стану черги | JSON-файл; атомарний запис (тимчасовий файл + перейменування); після перезапуску «Завантажується» → «В черзі» |
| Тимчасові `.part`-файли | Дані пишуться в `name.part`, і лише після повного успіху — перейменування в `name` |
| Повторні спроби з лімітом і затримкою | Класифікація помилок: що повторювати (тайм-аут, обрив, 5xx, 429), що ні (404, 403, помилка TLS); експоненційна затримка, яку можна перервати скасуванням |
| Тайм-аути | Тайм-аут з'єднання + «надто повільно N секунд», а не загальний ліміт на весь файл |
| Перевірка HTTP-статусу | Тіло відповіді 404/500 **не** повинне потрапити в `.part` |
| Перевірка TLS-сертифіката | Перевірка ввімкнена завжди; її вимкнення — не «фікс», а дірка |
| Відновлення через Range | `Range: bytes=N-` → очікуємо `206` і коректний `Content-Range`; `200` замість `206` → сервер ігнорує Range, починаємо з нуля |
| `ETag` / `Last-Modified` | `If-Range`: якщо ресурс змінився, сервер сам віддасть `200` з повним тілом → починаємо заново |
| Завершення зупиняє й приєднує потоки | `std::jthread` + `std::stop_token`: деструктор просить зупинку і чекає. Ніхто не має «зависнути» в `sleep` чи в мережі |
| Тестовий HTTP-сервер | Сервер **у процесі тестів** з керованою поведінкою: обрив, 404, зміна ресурсу, без Range |

## Рішення, які треба прийняти до коду

Як і в file-manager, спочатку домовляємось про поведінку, потім пишемо.
✅ **Прийнято** (усі рекомендації) — див. розділ «Поведінка» в [README.md](../README.md).

1. **Інтерфейс.** Консольний цикл команд (`add <url> [файл]`, `list`, `pause <id>`, `resume <id>`,
   `cancel <id>`, `limit <n>`, `exit`), поки завантаження йдуть у фоні? Чи «одноразовий» запуск
   `dm url1 url2 ...` з живим прогресом? Перший варіант ближчий до вимог (пауза/продовження).
2. **Як показувати прогрес.** Команда `list` на запит, чи окремий потік, що перемальовує рядки?
   Перемальовування заважає вводу команд — подумай, як їх розвести.
3. **Куди зберігати.** Тека завантажень за замовчуванням; ім'я файлу — з URL; що робити, якщо
   файл з таким ім'ям уже є (додати ` (1)`? помилка?). А якщо дві задачі в черзі ведуть в один
   і той самий файл (і в один `.part`)?
4. **Ліміти за замовчуванням.** Скільки паралельних завантажень, скільки спроб, яка затримка.
5. **Що робити з `.part` при скасуванні** — видаляти (рекомендую) чи лишати.

## Крок 0. Каркас і залежності (1 день)

Найризикованіший крок: у MinGW від CLion **немає libcurl**. Почни з нього, поки немає коду.

### Що зробити
1. `CMakeLists.txt` як у file-manager (C++20, попередження, `-Werror=return-type`).
2. Залежності через `FetchContent`:
   - **libcurl** — збирається з вихідних кодів. Для Windows обери TLS-бекенд **Schannel**
     (`CURL_USE_SCHANNEL ON`, `CURL_USE_OPENSSL OFF`): він вбудований у Windows і бере сертифікати
     з системного сховища, тож не треба ні OpenSSL, ні файлу `cacert.pem`. Вимкни зайве
     (`BUILD_CURL_EXE`, `BUILD_TESTING`, libpsl, libssh2, zlib, brotli, zstd, nghttp2, libidn2),
     збирай статично (`BUILD_SHARED_LIBS OFF`). Ціль для лінкування — `CURL::libcurl`.
   - **nlohmann/json** — header-only, ціль `nlohmann_json::nlohmann_json`.
   - **GoogleTest** — як у file-manager.
   - **cpp-httplib** — лише для тестів (крок 5), header-only HTTP-сервер.
3. «Димовий» `main.cpp`: `curl_version()` у консоль + одне завантаження `https://example.com/`
   у рядок. Якщо отримав `200` і HTML — збірка, TLS і мережа працюють.

> ⚠️ Цю комбінацію (curl + Schannel + MinGW GCC 15) я не перевіряв на твоїй машині. Якщо
> конфігурація curl падає — принеси вивід помилки, розберемо. Запасний варіант — бінарна
> збірка curl для MinGW з curl.se/windows, підключена через `find_package(CURL)`.

### Що вивчити
- Опції `FetchContent` для чужих проєктів: `set(... CACHE BOOL "" FORCE)` **до** `FetchContent_MakeAvailable`.
- Чим статична бібліотека з залежностями відрізняється від динамічної (які системні `.lib` потрібні
  Schannel — CMake curl додає їх сам, але подивись, що саме: `ws2_32`, `crypt32`, `secur32`...).

### Перевір себе
- Чому з TLS-бекендом Schannel не потрібен файл з кореневими сертифікатами, а з OpenSSL — потрібен?

## Крок 1. Одне завантаження в `.part` (2–3 дні)

### 1.1 Глобальна ініціалізація
`curl_global_init(CURL_GLOBAL_DEFAULT)` — **один раз**, у головному потоці, **до** створення
робочих потоків; `curl_global_cleanup()` — після того, як усі потоки зупинено. Зроби RAII-клас.

### 1.2 RAII для easy handle
`CURL*` з `curl_easy_init()` / `curl_easy_cleanup()`. Найпростіше — `std::unique_ptr` з власним
deleter'ом. Один handle — один потік; **ніколи** не ділити handle між потоками.

### 1.3 Одна спроба
Орієнтир сигнатури:
```cpp
TransferResult download_once(const TransferRequest& request, TransferObserver& observer);
```
- `CURLOPT_URL`, `CURLOPT_FOLLOWLOCATION`, `CURLOPT_MAXREDIRS`;
- `CURLOPT_WRITEFUNCTION` + `CURLOPT_WRITEDATA` — твій об'єкт, який пише у файл;
- `CURLOPT_HEADERFUNCTION` — збираєш статус, `Content-Length`, `Content-Range`, `ETag`, `Last-Modified`;
- `CURLOPT_ERRORBUFFER` — людський текст помилки;
- після `curl_easy_perform`: `CURLcode` **і** `CURLINFO_RESPONSE_CODE` — це дві різні помилки.

### 1.4 `.part` і фінальне перейменування
Пишеш у `name.part`; після успіху — `std::filesystem::rename(part, final, ec)`.

### Пастки
- **Тіло 404 потрапляє у файл.** libcurl вважає 404 успішним обміном (`CURLE_OK`). Рішення:
  дізнатися статус **до** першого запису (заголовки приходять раніше за тіло), і не писати тіло
  невдалої відповіді. `CURLOPT_FAILONERROR` — простіше, але подумай, що він втрачає.
- **Редиректи.** Header-callback бачить заголовки **кожної** відповіді ланцюжка (`301`, потім `200`).
  На кожному новому рядку статусу (`HTTP/...`) скидай зібране.
- **Write-callback повертає менше, ніж отримав** → libcurl перериває передачу (`CURLE_WRITE_ERROR`).
  Так і треба реагувати на помилку запису на диск.
- Callback'и — це C-функції: `static` функція або лямбда без захоплення, `void* userdata` → твій
  об'єкт через `static_cast`. Винятки **не можна** випускати з callback'а назовні в C-код.
- Заголовки HTTP нечутливі до регістру (`etag`, `ETag`).
- **Стиснення.** Не вмикай `CURLOPT_ACCEPT_ENCODING`: з `gzip` розміри й Range стосуються
  стиснених байтів, а у файл пишуться розпаковані → відновлення ламається.

### Готово, коли
Димовий запуск завантажує реальний файл по HTTPS, а для неіснуючого URL `.part` не лишає
сміття з HTML-сторінкою 404.

### Перевір себе
- Що буде з `.part`, якщо програму вбили посеред завантаження? А з фінальним файлом?

## Крок 2. Черга і пул працівників (3 дні)

### Що зробити
1. **Стани задачі** і дозволені переходи — спочатку таблицею на папері:
   `Queued → Downloading → Completed | Failed | Paused | Canceled`, `Paused → Queued`,
   `Failed → Queued` (ручний повтор?), `Downloading → Queued` (між повторними спробами?).
2. `DownloadManager`: `add(url, target) → TaskId`, `pause(id)`, `resume(id)`, `cancel(id)`,
   `snapshot() → std::vector<TaskInfo>` (копія для UI, щоб UI не тримав mutex).
3. N потоків `std::jthread`, кожен: взяти задачу з черги → завантажити → оновити стан → наступна.
4. Чекання роботи — `std::condition_variable_any::wait(lock, stop_token, predicate)`:
   ця перегрузка прокидається і при появі задачі, і при запиті зупинки.
5. **Шов для тестів.** Менеджер не викликає `download_once` напряму, а отримує «виконавця
   завантаження» ззовні (у конструкторі: `std::function` або абстрактний інтерфейс). У `main` —
   справжній libcurl, у тестах — фейк, яким керує тест (блокується до сигналу, повертає потрібну
   помилку). Так пул, стани й ліміт паралельності тестуються без мережі й без `sleep`.

### Готово, коли
Тест з фейковим виконавцем: 10 задач, ліміт 3 → одночасно активних ніколи не більше 3, усі 10
завершились, деструктор менеджера не висить.

### Що вивчити
- `std::jthread`, `std::stop_token`, `std::stop_source`, `std::stop_callback`.
- Чому для `stop_token` потрібна саме `condition_variable_any`, а не `condition_variable`.
- `std::scoped_lock` / `std::unique_lock`; чому `notify_*` можна робити після звільнення mutex.

### Пастки
- **Мережа під mutex.** `curl_easy_perform` під замком = усі інші потоки й UI стоять. Під mutex —
  лише взяти задачу / змінити стан.
- **Ліміт паралельності** — це кількість потоків, а не «скільки задач у стані Downloading»
  (останнє — для перевірки в тестах).
- **Порядок знищення.** Члени класу знищуються у зворотному порядку оголошення: потоки мають
  зупинитися **до** знищення mutex/черги, якими вони користуються → `jthread`-и оголошуються останніми.
- Зміна ліміту «на льоту» — розширення, не обов'язково.

### Перевір себе
- Робочий потік чекає на `cv`, і в цей момент викликали деструктор менеджера. Що його розбудить?

## Крок 3. Прогрес, тайм-аути, повторні спроби, скасування (3–4 дні)

### 3.1 Прогрес і швидкість
- `CURLOPT_XFERINFOFUNCTION` + `CURLOPT_XFERINFODATA` + `CURLOPT_NOPROGRESS 0`.
- Лічильники (`downloaded`, `total`) — `std::atomic<std::int64_t>` або під mutex разом зі станом.
- Швидкість: байти за останні ~2–3 с (`steady_clock`, не `system_clock`), а не «всього / весь час».
- Не забудь про зміщення при відновленні: прогрес = вже є в `.part` + отримано зараз.

### 3.2 Скасування й пауза
- xferinfo-callback викликається регулярно, навіть коли дані не йдуть → перевір у ньому
  `stop_token` / прапорець задачі й поверни ненуль → `CURLE_ABORTED_BY_CALLBACK`.
- Пауза і скасування переривають однаково; різниця — **після**: пауза лишає `.part`, скасування видаляє.
- Розрізняй, хто перервав: користувач (пауза/скасування) чи завершення програми.

### 3.3 Тайм-аути
- `CURLOPT_CONNECTTIMEOUT` — з'єднання.
- `CURLOPT_LOW_SPEED_LIMIT` + `CURLOPT_LOW_SPEED_TIME` — «повільніше X байт/с протягом T с».
- `CURLOPT_TIMEOUT` (на всю передачу) для великих файлів шкідливий — поясни собі чому.

### 3.4 Повторні спроби
- Чиста функція класифікації: `CURLcode` + HTTP-статус → «повторювати / ні». Це зручно тестувати без мережі.
- Затримка: експоненційна (1, 2, 4, 8 с...) з верхньою межею; `Retry-After` для 429/503 — бонус.
- Чекати затримку **не** через `std::this_thread::sleep_for`: скасування має перервати очікування →
  `cv.wait_for(lock, stop_token, delay, predicate)`.
- Повторна спроба після обриву — це вже **відновлення** (крок 4), а не завантаження з нуля.
  Поки кроку 4 немає, повтор чесно починає з нуля (обрізає `.part`); на кроці 4 це місце
  замінюється на відновлення.

### Пастки
- `CURLE_ABORTED_BY_CALLBACK` — **не** помилка для повтору.
- Помилки TLS (`CURLE_PEER_FAILED_VERIFICATION` та ін.) — не повторювати і не «лікувати»
  вимкненням `CURLOPT_SSL_VERIFYPEER`.
- Schannel може не перевірити відкликання сертифіката без доступу до мережі CRL/OCSP. Якщо зіткнешся —
  почитай про `CURLOPT_SSL_OPTIONS` / `CURLSSLOPT_REVOKE_BEST_EFFORT` і запиши рішення в README.

## Крок 4. Збереження стану і Range (3–4 дні)

### 4.1 Стан черги в JSON
- Для кожної задачі: id, URL, шлях, стан, `ETag`, `Last-Modified`, загальний розмір (якщо відомий).
- Зберігати **при зміні стану**, а не на кожен шматок даних.
- Атомарний запис: `state.json.tmp` → `rename` поверх `state.json`. Обірваний запис не повинен
  зіпсувати стан.
- Під час завантаження: `Downloading` → `Queued` (програма впала посеред роботи).
- Скільки вже завантажено — бери з **реального розміру `.part`**, а не з JSON: файл — джерело правди.
- Битий / відсутній JSON — не падати: почати з порожньої черги і повідомити.

### 4.2 Відновлення
Чисті функції в `resume.cpp` (тестуються без мережі):
- розбір `Content-Range: bytes 1000-4999/5000` (а ще `bytes */5000` для 416);
- рішення за (статус, `Content-Range`, зміщення) → «дописувати» / «почати з нуля» / «помилка».

Запит: `CURLOPT_RESUME_FROM_LARGE` (або `CURLOPT_RANGE`) + заголовок `If-Range` зі збереженим
`ETag` (або `Last-Modified`) через `CURLOPT_HTTPHEADER` (`curl_slist`, теж RAII).

| Відповідь | Що робити |
|---|---|
| `206`, `Content-Range` починається з твого зміщення | Дописувати в кінець `.part` |
| `206`, але інше зміщення | Помилка / почати з нуля — не склеювати шматки навмання |
| `200` | Сервер ігнорує Range **або** ресурс змінився (`If-Range`) → обрізати `.part` до 0 і писати з початку |
| `416` | Зміщення ≥ розміру: можливо, файл уже повний — звір з `total` з `Content-Range: bytes */N` |

### Пастки
- Рішення «дописувати чи обрізати» треба прийняти **до** першого запису в файл — тобто в момент,
  коли заголовки вже прийшли (див. крок 1.3).
- Слабкий `ETag` (`W/"..."`) **не можна** використовувати в `If-Range` — тоді `Last-Modified` або заново.
- Немає ні `ETag`, ні `Last-Modified` → безпечно відновити неможливо → заново.
- Відкривати `.part` у режимі дописування (`std::ios::app`) чи з позиціюванням — обери і поясни.

### Перевір себе
- Сервер повернув `200` на запит з Range, а ти дописав тіло в кінець `.part`. Що буде з файлом?
  Який тест це зловить?

## Крок 5. Тести з локальним сервером (3–4 дні, частково паралельно з кроками 1–4)

### Сервер
`cpp-httplib` у процесі тестів: `bind_to_any_port("127.0.0.1")` → вільний порт,
`listen_after_bind()` в окремому потоці, `stop()` у `TearDown`. На MinGW httplib потребує
`ws2_32` і `_WIN32_WINNT` не нижче Windows 10 (`0x0A00`) — інакше помилка вже на `#include`.
Підніми сервер і перший тест **одразу після кроку 1** — далі кожен крок перевіряється ним.
Обробники керують поведінкою:

| Сценарій | Як змоделювати |
|---|---|
| Звичайне завантаження | Відомий вміст (наприклад, 1 МБ псевдовипадкових байтів із фіксованим seed) |
| 404 / 500 | Обробник ставить статус |
| 500, потім 200 | Лічильник запитів у фікстурі |
| Обрив посередині | Content provider, що віддає частину і повертає `false` |
| Сервер без Range | Завжди `200` з повним тілом (перевір, як httplib сам обробляє Range, і обійди це) |
| Ресурс змінився | Між запитами змінюється вміст і `ETag` |
| Повільний сервер | Затримки в provider'і → тайм-аут |
| Ліміт паралельності | Атомарний лічильник «зараз активних обробників» і його максимум |

### Тести-критерії з README
- **Побайтовий збіг після відновлення:** обрив → відновлення → порівняти файл з оригіналом.
- **Ліміт паралельності:** 10 задач, ліміт 3 → максимум активних на сервері = 3.
- **Завершення приєднує потоки:** знищити менеджер посеред завантажень → тест не висить
  (GoogleTest не має вбудованого тайм-ауту — подумай, як це перевірити: час виконання, `std::future::wait_for`).

### Пастки
- Тести з потоками **не повинні** покладатися на `sleep` «щоб встигло». Чекай події
  (стан задачі змінився) з верхньою межею часу.
- Фікстура-пісочниця для файлів — як у file-manager (`test_sandbox.hpp` можна перенести).
- Чисті функції (`resume`, `retry`, JSON) — звичайні швидкі тести без сервера.

## Крок 6. Графічний інтерфейс на Qt (1 тиждень, після готового ядра)

Qt — **лише шар UI**: `dm_core` не знає про Qt, мережа й потоки лишаються на libcurl + `std::jthread`.
`QNetworkAccessManager` і `QThread` не використовуємо.

### 6.0 Середовище
- Встановити Qt 6 (Online Installer, компонент для MinGW). Qt зібраний **своєю** версією MinGW,
  не GCC 15 від CLion → у CLion окремий toolchain з MinGW від Qt, і весь проєкт (разом з libcurl
  і тестами) збирається ним. Змішувати бібліотеки різних GCC — ризик невідповідності ABI.
- Перший тест середовища: порожнє вікно `QApplication` + `QMainWindow`; `windeployqt` для запуску поза CLion.

### 6.1 Що зробити
1. Окрема ціль `dm_gui` (`find_package(Qt6 REQUIRED COMPONENTS Widgets)`, `qt_standard_project_setup()`,
   `qt_add_executable`), лінкується з `dm_core`. Консольна ціль лишається.
2. Головне вікно: таблиця завантажень (ім'я, прогрес, швидкість, стан), поле URL + «Додати»,
   кнопки «Пауза / Продовжити / Скасувати» для вибраного рядка.
3. Модель таблиці — власний `QAbstractTableModel` поверх `snapshot()` ядра.
4. Оновлення: `QTimer` у GUI-потоці раз на ~200 мс бере `snapshot()` і повідомляє модель
   (`dataChanged`, а для нових рядків — `beginInsertRows`/`endInsertRows`).
5. Закриття вікна — та сама логіка, що й `exit`: зберегти стан, зупинити й приєднати потоки.

### Що вивчити
- Цикл подій Qt: чому GUI-потік не можна блокувати (ні мережею, ні `join`, ні довгим mutex).
- Model/View: `rowCount`, `columnCount`, `data`, ролі (`Qt::DisplayRole`), делегат для прогрес-бару — бонус.
- Сигнали/слоти; `Qt::QueuedConnection` — як альтернатива таймеру (порівняй підходи).
- Володіння об'єктами в Qt (дерево батьків) vs `std::unique_ptr` у твоєму ядрі.

### Пастки
- **Робочі потоки не торкаються віджетів і моделі.** Лише GUI-потік. Таймер + `snapshot()` це гарантує.
- Рядки: `QString` (UTF-16) ↔ UTF-8 ядра — `QString::fromUtf8` / `toUtf8`, шляхи — через
  `std::filesystem::path` (`QString::toStdWString`), а не через локальне кодування.
- Ідентифікація рядка таблиці — за `TaskId`, а не за номером рядка (порядок може змінюватися).
